# 에이전트 팀 아키텍처 패턴 전투 교리 (Harness Doctrine)

> **출처**: revfactory/harness (오픈소스, Apache 2.0) — 개념적 이식
> **목적**: `agent-forge`가 새 스킬 설계 시 팀 구조 패턴을 체계적으로 선택하도록 지원

---

## 1. 실행 모드 선택: 팀 vs 서브에이전트

새 에이전트를 설계할 때, 가장 먼저 **실행 모드**를 결정한다.

```
에이전트가 2개 이상인가?
├── Yes → 에이전트 간 실시간 통신(교차 검증/발견 공유)이 필요한가?
│         ├── Yes → 팀 모드 (기본값): 더 높은 품질
│         └── No → 서브에이전트도 가능: 결과 전달만 필요한 경우
└── No (1개) → 서브에이전트: 단일 에이전트는 팀 불필요
```

**핵심 원칙**: 팀이 기본이다. 서브에이전트를 선택할 때는 "팀원 간 통신이 정말 불필요한가?"를 자문한다.

## 2. 6대 아키텍처 패턴 분류표

### 패턴 1: 파이프라인 (Pipeline) — 순차 의존
```
[분석] → [설계] → [구현] → [검증]
```
- **적합한 경우**: 각 단계가 이전 단계 산출물에 강하게 의존
- **예시**: 신학 논문 석의 — 본문분석 → 역사비평 → 신학주석 → 설교초안
- **주의**: 병목이 전체를 지연시킴. 각 단계를 최대한 독립적으로 설계할 것.
- **팀 모드 적합성**: ⭐⭐ 팀 이점 제한적. 파이프라인 내 병렬 구간이 있으면 팀 유용.

### 패턴 2: 팬아웃/팬인 (Fan-out / Fan-in) — 병렬 독립
```
          ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
          └→ [전문가C] ─┘
```
- **적합한 경우**: 동일 입력에 대한 서로 다른 관점/영역의 분석이 필요
- **예시**: 심층 리서치 — 공식문서/미디어/커뮤니티/학술 동시 조사 → 통합 보고
- **주의**: 통합 단계의 품질이 전체를 결정.
- **팀 모드 적합성**: ⭐⭐⭐ 팀 모드의 가장 자연스러운 패턴. **반드시 팀으로 구성.** 실시간 발견 공유가 품질을 크게 높인다.

### 패턴 3: 전문가 풀 (Expert Pool) — 상황별 선택
```
[라우터] → { 전문가A | 전문가B | 전문가C }
```
- **적합한 경우**: 입력 유형에 따라 다른 처리가 필요
- **예시**: 신학 검색 — 역사비평/조직신학/목회신학 전문가 중 해당 영역만 호출
- **주의**: 라우터의 분류 정확도가 핵심.
- **팀 모드 적합성**: ⭐ 서브에이전트가 더 적합. 필요한 전문가만 선택 호출하므로.

### 패턴 4: 생성-검증 (Producer-Reviewer) — 품질 보증
```
[생성] → [검증] → (문제 시) → [생성] 재실행
```
- **적합한 경우**: 산출물의 품질 보장이 중요하고 검증 기준이 명확할 때
- **예시**: 논문 번역 — 번역 에이전트 → 신학 용어 검수 에이전트
- **주의**: 무한 루프 방지를 위해 **최대 재시도 2~3회** 설정 필수.
- **팀 모드 적합성**: ⭐⭐⭐ 생성자↔검증자 간 실시간 피드백 교환 가능.

### 패턴 5: 감독자 (Supervisor) — 동적 분배
```
          ┌→ [워커A]
[감독자] ─┼→ [워커B]    ← 감독자가 상태를 보고 동적 분배
          └→ [워커C]
```
- **적합한 경우**: 작업량이 가변적이거나 런타임에 분배를 결정해야 할 때
- **예시**: 대규모 파일 처리 — 감독자가 목록을 분석하고 워커들에게 배치 할당
- **팬아웃과의 차이**: 팬아웃은 사전에 고정 분배, 감독자는 진행 중 동적 조정.
- **팀 모드 적합성**: ⭐⭐⭐ 공유 작업 목록이 감독자 패턴과 자연스럽게 매칭.

### 패턴 6: 계층적 위임 (Hierarchical Delegation) — 재귀적 분해
```
[총사령관] → [지대장A] → [분대원A1, A2]
           → [지대장B] → [분대원B1, B2]
```
- **적합한 경우**: 복잡한 문제를 단계적으로 분해해야 할 때
- **예시**: 대형 콘텐츠 제작 — 총괄 → 파트별 감독 → 실무 작업자
- **주의**: 깊이가 깊을수록 조율 복잡도가 기하급수적으로 증가.
- **팀 모드 적합성**: ⭐⭐ 중간 레이어 에이전트가 팀과 서브에이전트를 혼용.

## 3. 에이전트 분리 기준 (4축 판단)

새 스킬 설계 시, 에이전트를 몇 개로 분리할지 다음 4축으로 판단한다:

| 축 | 질문 | Yes → 분리 | No → 통합 |
|---|---|---|---|
| **전문성** | 각 에이전트가 서로 다른 전문 지식이 필요한가? | ✅ 분리 | 통합 가능 |
| **병렬성** | 동시에 수행 가능한 독립적 작업인가? | ✅ 분리 | 순차 실행 |
| **컨텍스트** | 각 작업이 서로 다른 정보 세트를 필요로 하는가? | ✅ 분리 | 공유 가능 |
| **재사용성** | 이 에이전트를 다른 하네스에서도 사용할 수 있는가? | ✅ 분리 | 특화 가능 |

**실용 규칙**: 에이전트 1개당 5~6개 작업이 적정. 그 이상이면 분리를 고려.
