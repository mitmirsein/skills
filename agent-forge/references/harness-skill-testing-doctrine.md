# 스킬 품질 검증 프레임워크 (Harness Testing Doctrine)

> **출처**: revfactory/harness — skill-testing-guide.md + qa-agent-guide.md 개념 이식 (Apache 2.0)
> **목적**: `agent-forge`가 생성한 스킬을 실전 검증하는 표준 방법론. 우리 시스템에 기존에 없던 것.

---

## 1. With-Skill vs Baseline 비교 테스트

스킬의 효과를 증명하는 가장 강력한 방법. **동일 프롬프트**를 두 가지 조건으로 동시 실행한다.

```
테스트 프롬프트 (동일)
    ├── [With-Skill] → 스킬 활성화 실행    → 출력 A
    └── [Baseline]  → 스킬 없이 실행      → 출력 B

평가: A vs B 비교 → 품질 점수, 완성도, 정확도 채점
```

### 실전 워크플로우

```
1. 테스트 프롬프트 2~3개 작성 (아래 기준 참조)
2. With-Skill 실행 → 출력 저장
3. Baseline 실행  → 출력 저장
4. 두 출력을 assertion 기준으로 비교 채점
5. 차이가 없거나 With-Skill이 열등하면 → 스킬 수정 후 재테스트
```

## 2. 테스트 프롬프트 작성 원칙

### ❌ 나쁜 예
```
"PDF를 처리하라"               # 너무 추상적
"신학 논문을 번역하라"          # 구체성 없음
```

### ✅ 좋은 예
```
"이 독일어 신학 논문 3장의 '화해' 개념 섹션(pp.47-52)을
한국어 개혁신학 용어로 번역하되, 바르트의 화해론 용어집을 참조해줘."
```

### 커버리지 3종 세트
1. **핵심 사용 사례 1개**: 가장 일반적인 트리거 상황
2. **엣지 케이스 1개**: 불완전한 입력, 예외 상황
3. **복합 작업 1개** (선택): 두 가지 이상의 스킬 기능을 조합하는 경우

### 프롬프트 다양성 체크
- [ ] 공식적 / 캐주얼 톤 혼합
- [ ] 명시적 / 암시적 의도 혼합
- [ ] 단순 / 복잡 작업 혼합

## 3. Assertion 기반 채점 (정량 평가)

주관적 체감이 아니라, 미리 정의한 **검증 조건(Assertion)**으로 통과/실패를 판정한다.

```python
# 예시 — theology-translator 스킬 검증
assertions = {
    "한국어 사용": lambda out: "믿음으로 말미암아" in out or "칭의" in out,
    "원문 인용 포함": lambda out: "(" in out and ")" in out,
    "각주 형식 준수": lambda out: "[^" in out,
    "출력 길이 적절": lambda out: 300 < len(out) < 5000,
}
# 모든 assertion 통과 시: PASS → 배치
# 1개라도 실패 시: FAIL → 스킬 수정 후 재실행
```

**규칙**: 스킬 배치 전 최소 1개의 assertion을 반드시 정의한다. `evals/evals.json`에 저장.

## 4. QA: 경계면 교차 비교 (Integration Coherence)

> 가장 자주 놓치는 결함: 두 컴포넌트가 각각 "정상"이지만 **연결 지점에서 계약이 어긋나는** 경우.

단일 컴포넌트가 올바른지 확인하는 것으로는 부족하다. **경계면(Boundary)을 교차 비교**해야 한다.

### 주의해야 할 경계면 패턴

| 경계면 | 불일치 예시 | 검증 방법 |
|---|---|---|
| 스킬 → 다음 스킬 | 스킬 A 출력이 스킬 B 입력 형식과 다름 | 두 스킬의 input/output 스키마 교차 비교 |
| 에이전트 → 파일 저장 | 에이전트가 예상 경로와 다른 곳에 저장 | 저장 경로와 참조 경로 대조 |
| 서브에이전트 → 메인 | 서브에이전트 출력이 메인이 기대하는 구조와 다름 | output 스키마 명시 + 검증 |
| 트리거 → 실행 | 스킬이 의도한 상황에서 트리거되지 않음 | Description 재검토 |

### QA 에이전트 설계 원칙 (중요)
- "파일이 존재하는가?"가 아니라 **"이 파일의 내용이 다음 단계의 기대와 일치하는가?"**를 검증한다.
- QA는 **전체 완성 후 1회**가 아니라 **각 모듈 완성 직후 점진적으로(Incremental)** 실행한다.
- 빌드 성공 ≠ 정상 동작. 런타임 동작까지 검증하라.

## 5. 반복 개선 루프 (Iteration Protocol)

```
스킬 작성
    ↓
3종 테스트 프롬프트로 With-Skill vs Baseline 실행
    ↓
Assertion 채점
    ├── 모두 PASS → 배치 및 gotchas.md 업데이트
    └── FAIL 항목
        ├── Description 문제 → Description 재작성 후 재실행
        ├── 본문 로직 문제  → 해당 섹션 Why-First 원칙으로 재작성
        └── 구조 문제       → 아키텍처 패턴 재검토
```

**규칙**: 최대 3회 반복. 3회 후에도 실패 시 → 스킬 범위 재정의(Scope Re-definition).

## 6. Description 트리거 검증

스킬이 올바른 상황에서 트리거되고, 잘못된 상황에서는 트리거되지 않는지 검증한다.

```
검증 1 (TRUE 케이스):  스킬이 트리거 되어야 하는 프롬프트로 실행
    → 스킬이 호출되었는가? ✅

검증 2 (FALSE 케이스): 스킬이 트리거 되면 안 되는 유사 프롬프트로 실행
    → 스킬이 미호출 되었는가? ✅

둘 다 통과 시 트리거 메커니즘 승인.
```
